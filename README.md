# MediGuard — medicine storage monitoring prototype

MediGuard is a student-built prototype that combines an ESP32, a temperature/humidity sensor, simple fan-and-flap control, and a browser dashboard. The goal is to explore whether low-cost electronics can make storage conditions easier to monitor and review.

> **Prototype only:** This project has not been validated as a medical storage device. The default 2–8 °C temperature and 30–60% relative-humidity limits are demo settings, not universal requirements. Follow the storage instructions for the specific medicine. Do not use this prototype alone to decide whether medicine is safe.

## What is included

- ESP32 sketch for a DHT22 sensor, OLED, fan MOSFET outputs, servos, buzzer, and Wi-Fi reporting.
- Flask API that receives readings, stores them in SQLite, and tracks configured-limit alerts.
- Browser dashboard with latest readings, charts, recent alerts, editable limits, and CSV export.
- A demo mode that generates **simulated** readings so the dashboard can be explored without hardware.

The low-temperature logic stops cooling and reports a warning. The second fan is not treated as a heater: without measuring ambient temperature, blowing room air cannot guarantee that the chamber will warm up.

## Try the dashboard without hardware

Requires Python 3.10 or newer.

1. Open a terminal in `backend/`.
2. Install dependencies:

   ```bash
   python -m pip install -r requirements.txt
   ```

3. Start demo mode:

   ```bash
   python app.py --demo
   ```

4. Open [http://127.0.0.1:5000](http://127.0.0.1:5000).

Demo readings are generated by software. They are not measurements from a physical box and must not be presented as hardware test results.

## Connect the ESP32

### Configure the server

Use a custom development API key. On Windows PowerShell:

```powershell
$env:MEDIGUARD_KEY = "replace-with-a-long-random-key"
python app.py
```

On macOS/Linux:

```bash
export MEDIGUARD_KEY="replace-with-a-long-random-key"
python app.py
```

The server prints the computer's LAN address. Put that address in `SERVER_URL` in the ESP32 sketch, ending with `/api/readings`. For example:

```cpp
const char* SERVER_URL = "http://192.168.1.40:5000/api/readings";
```

The computer and ESP32 need to be on the same network. Allow the server through the computer's firewall if needed. This is a local development server; do not expose it directly to the public internet.

### Configure the sketch

Open `esp32/mediguard_esp32/mediguard_esp32.ino` in Arduino IDE and set `WIFI_SSID`, `WIFI_PASS`, `SERVER_URL`, and `API_KEY`. Do not commit real Wi-Fi credentials or private keys.

Install these libraries from Arduino Library Manager:

- Adafruit GFX Library
- Adafruit SSD1306
- DHT sensor library (Adafruit)
- Adafruit Unified Sensor (if prompted)
- ESP32Servo
- ArduinoJson 7

`WiFi.h`, `HTTPClient.h`, and `Wire.h` come with the ESP32 Arduino core.

### GPIOs currently used by the sketch

| Function | GPIO |
|---|---:|
| DHT22 data | 4 |
| OLED SDA / SCL | 21 / 22 |
| Cooling servo signal | 27 |
| Warm-air servo signal | 14 |
| Cooling fan MOSFET gate | 26 |
| Warm-air fan MOSFET gate | 25 |
| Buzzer signal | 33 |

Treat this as the sketch's current pin map, not a guarantee for every development board. Check the silkscreen and verify wiring before applying power. Confirm the servo's closed/open angles mechanically; the current sketch assumes 180° is closed for the cooling flap and 0° is closed for the warm-air flap.

## Power and build notes

- The two fans in the current design are **12 V DC, 0.60 A each**. Power them from a suitable 12 V supply through appropriately rated MOSFET switching circuits. Do not connect a fan directly to an ESP32 GPIO.
- Use a regulated 12 V supply and a 12 V-to-5 V buck converter for 5 V loads. Measure the buck output before connecting electronics.
- Share ground between the ESP32, buck converter, and fan-switching circuits.
- Never apply 12 V directly to the ESP32, DHT22, OLED, or SG90 servos.
- Keep electronics isolated from ice and meltwater; use sealed ice packs and a water tray.
- Verify the actual board pinout, MOSFET gate-drive suitability, servo travel, and fan airflow direction before installing the parts in the enclosure.

## Temperature limits and behavior

The server defaults to 2–8 °C and 30–60% RH as configurable demonstration limits. The firmware starts cooling airflow at 7 °C, stops it below 7 °C, and reports a low-temperature condition below 2 °C. These are prototype control settings, not medical guidance. The DHT22 has not been calibrated as part of this repository, and the box's temperature uniformity and hold time have not been validated.

## API endpoints

- `POST /api/readings` — accept a device reading; requires the `X-API-Key` header.
- `GET /api/latest` — latest reading and whether it is recent.
- `GET /api/readings?minutes=60` — historical readings.
- `GET /api/stats?minutes=60` — summary statistics.
- `GET /api/alerts?limit=15` — recent alert events.
- `GET /api/settings` and `PUT /api/settings` — read/update limits.
- `GET /api/export.csv?minutes=0` — export readings (`0` means all stored readings).

The settings and export routes are intended for local prototype use, not an internet-facing deployment. Add authentication and transport security before exposing any service beyond a trusted development network.

## Tests

Install the backend dependencies, then from the repository root run:

```bash
python -m unittest discover -s tests -v
```

These tests exercise the Flask API and validation paths. They do not compile the Arduino sketch or replace testing with the actual ESP32, sensor, fan drivers, and servos.

## Known limitations / next work

- Run the end-to-end test with the actual ESP32 and verify the server receives fresh readings.
- Confirm the final sensor model and compare readings against a trusted thermometer/hygrometer.
- Add lid-switch events to the firmware and dashboard if the reed switch is installed.
- Test Wi-Fi/server outages and document how stale readings are shown.
- Measure temperature at multiple points in the chamber under realistic ambient conditions.
- Add ambient sensing if the design is expected to decide whether room air can help with a low-temperature condition.
- Review security before any non-local deployment.
